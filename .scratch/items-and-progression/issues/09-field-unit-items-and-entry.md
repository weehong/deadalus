# 09: The Field's Unit screen: Items and Progress entry

**What to build:** A Member opens a Unit and sees a heading of Project code, Block, Storey and Unit label, then their Subcontractor's Items there with Progression and latest entry. On each, an "Enter progress" form (numeric keypad, 0 to 100, optional note) records an entry that updates the Item in place, and a History disclosure lists past entries. Returning to the drill-down shows the moved Progression.

Underneath: `GET /api/v1/field/units/:unitId/items` (the Console's Item shape plus the heading fields, restricted to the Subcontractor's Items, 404 where it holds none); `POST /api/v1/field/items/:itemId/entries { value, note? }` (404 when the Item is not the Subcontractor's, including an unassigned Item; author `enteredByKind` member, `enteredById` the Member id, `enteredByName` the Member's name, `subcontractorName` snapshotted; the same one-transaction Progression update as the Console route; 201 with the Unit's Items); `GET /api/v1/field/items/:itemId/entries` with the same 404 rule.

Spec: `.scratch/items-and-progression/spec.md`. ADR-0003 applies.

**Blocked by:** 08 (The Field's Project, Block, Storey and Unit drill-down)

**Status:** complete

- [x] The Unit's Items read returns only the Subcontractor's Items and 404 otherwise; the entry route writes the Member author fields and updates Progression in one transaction, and is 404 for another Subcontractor's Item and for an unassigned Item; history follows the same rule; covered at the HTTP seam
- [x] All three routes appear in the OpenAPI document
- [x] The Field entry form and Item row reuse or mirror the Console components, each with a story and a test
- [x] The screen works at phone width in both locales, with validation messages associated with the field and focus handled
- [x] The Field e2e fake implements the routes and the e2e spec covers the list, a successful entry reflected in the drill-down Progression, a validation error and history; accessibility checks pass
